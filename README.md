# DIVA — 増配期待株の発掘エンジン

市場に正しく評価されていない増配期待企業を、全上場3,700銘柄から探して提示する。

保有管理と資金配分も持っているが、それは主目的ではない。発掘した銘柄を
「いくらで・どの枠に入れるか」を決めるための受け皿として付いている。

## 置き場所

`~/dev/diva`（Finder では **ken → dev → diva**）。

**デスクトップに置いてはいけません。** macOS は デスクトップ・書類 フォルダを
バックグラウンドのプログラムから隔離するので（TCC）、自動更新が毎週黙って失敗します。
実測で、デスクトップに置いていたときは LaunchAgent からフォルダ一覧すら読めず、
終了コード78で落ちてログも空のままでした。`~/dev` は隔離の対象外です。

## 保有銘柄はここだけで管理する

持株の管理は **このアプリ1本**。以前使っていた `portfolio-manager`
（`~/Desktop/クロード/portfolio-manager`）は参照専用で止めてあり、そちらを開いても
数字は更新されない。

2つで管理していたとき、実際にズレが出た。ヒラノテクシード(6245)を 2026-09-20 に
売ったあと、portfolio-manager 側には154株持ったまま残っていて、資産額が
23万円ぶん多く見えていた。**同じものを2か所で持つと、必ずどちらかが古くなる。**

株数と取得単価を直すのは 📊ポートフォリオ の「保有一覧」。売買として記録も残したい
ときは 💰資金投入 の「買う」「整理する」を使う。

## 使うとき（Finder でダブルクリックするだけ）

| ファイル | 何をするか | かかる時間 |
|---|---|---|
| **起動.command** | アプリをブラウザで開く | 数秒 |
| **更新.command** | 株価・配当・スコアを取り直す。終わったら数字の検算まで自動で走る | 約20分 |
| **自動更新の設定.command** | 毎週土曜9時の自動更新をオン／オフする（既定はオフ） | 数秒 |

**更新はアプリの中からもできる。** 左の「📥 データを更新」を押すと裏で
`scripts/scheduled_update.py` が走り（土曜の自動更新と同じもの）、進み具合が出る。
終わると自動で新しい数字に入れ替わる。パソコンで開いているときだけ出る
（クラウド版＝スマホからは更新できない）。ログは `logs/manual_update.log`。

更新.command で更新したときは、アプリの左の「🔄 読み込み直す」を押す。
押さないと最大10分は前の数字のまま出る。

データがいつ時点のものかは、**どの画面でも左に常に出ている**。
8日を超えると警告、21日を超えると「この数字で売買を決めないでください」と出る。

## 画面

| 画面 | 役割 |
|---|---|
| 🔭 発掘 | **本丸**。ゲートを通った銘柄をスコア順に並べ、未保有の銘柄を優先して出す |
| 📄 銘柄カルテ | 1銘柄を1枚で判断する。なぜ増配が続くか／指値／**棄却条件** |
| 🚨 監視 | 保有と候補の異変。減配・基準逸脱・指値到達 |
| 💰 資金投入 | 入金額を、スコアと業種の空き枠に合わせて割り振る |
| 📊 ポートフォリオ | 業種の偏り・配当月の偏り・YOC・増配の実績・指数との差 |
| 🧪 検証 | **スコアが本当に効くかを確かめる**。ここを通さずに重みを動かさない |
| 📖 使い方 | 指標の読み方と毎月の使い方。パーセンタイル・ヘム指数・配当性向・YOC の解説 |

**買う基準と売る基準は別物**として持っている。買うときは選択肢が3,700あるので厳しくてよいが、
売るのは税金・スプレッド・再投資先の確保というコストを払う行為なので、
「配当が壊れた」という**起きた事実**にだけ反応させる（`modules/sell_rules.py`）。
監視も資金投入も同じ判定を使うので、画面によって答えが変わることはない。

## スコアの考え方

5層 ＋ 減点。すべての内訳をカルテで開示する。

| 層 | 何を見るか |
|---|---|
| A 増配余力 | 増配を「出せる」か。配当性向・**ヘム指数**・FCFカバー率・ネットキャッシュ・負債の軽さ |
| B 増配意思 | 増配を「する気がある」か。連続増配・減配なし継続・DPS成長・**配当政策**（累進配当/DOE/性向目標を有報から自動検出） |
| C 原資成長 | 配当の元手が伸びているか。純利益・営業CF・ROE・営業利益率 |
| D 見過ごされ度 | 規模の小ささ・売買代金の薄さ・機関投資家保有の低さ＝カバー不足。PBR1倍割れ×増益 |
| E 割安 | **その銘柄自身の過去**と比べて割安か（自己ヒストリカル利回りパーセンタイル） |
| F 減点 | 高配当トラップ。異常高利回り×52週安値圏、利益とCFの乖離、性向の急上昇、希薄化 |

配当性向は**低いほど良いのではない**。30〜50% を満点とし、15% 未満は
還元する気がないとして減点する。

**配当性向は「直近の決算期の実績」。** その期に権利落ちした1株配当 × 株数 ÷ その期の
連結純利益で、分子と分母の決算期を必ずそろえる。証券会社や決算短信の数字は
たいてい**今期予想**ベースなので、利益が一時的に落ちた年は大きく食い違う。
有報の配当性向は親会社**単体**の数字なので、連結の会社には使わない
（2026-10-02 まで使っていて、小松製作所が 45% ではなく 92.7% と出ていた）。

**累進配当・DOE を掲げる会社**は、方針を掲げていて直近3年に減配が無ければ、
過去の減配回数や配当継続スコアの低さを売り理由にしない（`modules/sell_rules.py`）。

**発掘スコアと配当継続スコアは別物。**
発掘スコア（total）は「市場にまだ気づかれていないか」を含むので、大型株は構造的に
低く出る（三菱商事の見過ごされ度は8点、JR東日本は7点）。
**持っている株を評価するのは配当継続スコア（health）**で、こちらは市場の評価を入れず
「配当が続くか・増えるか」だけを見る。

## データ源と、その限界

| データ | 出どころ | 取れる長さ |
|---|---|---|
| 上場銘柄・33業種区分 | JPX 公式 `data_j.xlsx` | 常に最新 |
| 株価・配当・分割 | yfinance 一括ダウンロード | **2000年〜（20年超）** |
| 事業の内容・配当政策 | **EDINET**（金融庁）の有価証券報告書 | 最新 |
| EPS・ROE・自己資本比率・営業CF | **EDINET**「主要な経営指標等の推移」 | **5年分（確定値）** |
| 財務（PL/BS/CF・補助） | yfinance 個別取得 | 4〜5期分 |
| 権利確定日・会社予想配当 | yfinance | 直近 |

**EDINET が中核。** 有価証券報告書のXBRLには「主要な経営指標等の推移」として
5年分の EPS・1株配当・配当性向・ROE・自己資本比率・営業CF・従業員数が
構造化データで入っている。1社300KB で5年分が揃う。さらに「事業の内容」と
「配当政策」が日本語で取れるので、**何をやっている会社か**と
**累進配当・DOE を掲げているか**も分かる。

ROE・自己資本比率は、有報の値が連結と同じ会社のもの（純利益が一致する）ときだけ優先する。

`info["payoutRatio"]` は信用しない（実測で 480% という値を確認した）。
配当性向は DPS × 発行済株数 ÷ 純利益 で自前計算する。

## 開き方

Finder で `起動.command` をダブルクリック。ターミナルが開いてブラウザが立ち上がる。
**ターミナルの窓は開けたままにする**（閉じるとアプリも止まる）。終わるときは Control + C。

## 手で動かす場合

```bash
uv venv --python 3.11
uv pip install -r requirements.txt
```

```bash
# 保有データを portfolio-manager から取り込む（初回のみ）
uv run python scripts/import_legacy.py

# 資産の推移も引き継ぐ（初回のみ。推計として印を付けて入る）
uv run python scripts/import_legacy_history.py

# 「ほっといた場合」の比較対象（初回＋たまに）
uv run python scripts/fetch_benchmarks.py

# 全市場スキャン（約15分）
uv run python scripts/weekly_scan.py

# 有価証券報告書を取り込む（初回・約1時間。年1回でよい）
uv run python scripts/fetch_edinet.py --index --fetch

# 権利確定日・会社予想配当（約10分。月1回程度）
uv run python scripts/fetch_profiles.py --missing-only

# スコアの予測力を検証する（重みを動かす前に必ず）
uv run python scripts/validate_score.py

# 画面を開く
uv run streamlit run app.py
```

```bash
# 保有とウォッチリストの監視（通知内容を画面で確認）
uv run python scripts/daily_watch.py --dry-run

# 外部データ源が壊れていないかのチェック
uv run python scripts/selfcheck.py
```

## 定期実行

保有情報をリポジトリの外に出さないため、**DB はローカルの SQLite が唯一の正**。
したがって定期実行も Mac 側で動かす。`schedule/` の plist を
`~/Library/LaunchAgents/` に入れて `launchctl load` する。

GitHub Actions は外部データ源の健全性チェックだけを担当する
（JPX の一覧URLは過去に 404 になった実績があり、土曜のスキャンが動いてから
気づくのでは遅いため）。

## 注意

- 自分用のツールとして使う限り問題ないが、**スコアや推奨銘柄を他人に有償提供すると
  投資助言業に当たる**。外に出す場合は「判断基準と道具を売る」形に留めること。
- スコアの重みは現在すべて等ウェイト。検証を通った層だけ重みを上げる。
